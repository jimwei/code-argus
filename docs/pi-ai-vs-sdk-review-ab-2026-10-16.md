- **时间**：2026-10-14 06:50 → 2026-10-15（UTC）
- **机器**：`prm-g1-103`（10.32.4.103），隔离目录 `/tmp/argus-ab-c8cbf1e-20261014-gIH7A9`

## 一、结论

1. **pi-ai 明显更慢、更贵。** 同一真实 PR、同一模型与参数：48k 预算下两轮 pi-ai 都未能在 20 / 45 分钟上限内跑完（都卡在 logic-reviewer）；生产默认 160k 预算那轮虽然跑完，但用了 **63.4 分钟 / 9.46M tokens**，而 SDK 两轮都跑到 `review:complete`，只用 **14.6 / 39.7 分钟、4.05M / 3.64M tokens**。这与您在 103 上的生产观察一致。
2. **差距来自 agent 行为，而不是单请求速度或缓存。** pi-ai-r3 发出 191 条请求、完成 237 次工具调用；SDK 两轮只发 74 / 80 条、完成 92 / 75 次。缓存命中率几乎相同、pi-ai 甚至略高（pi-ai 92.7–94.8% vs SDK 89.9–92.9%）。
3. **输出（推理）token 放大最明显**：pi-ai-r3 输出 1.04M（其中推理 0.99M），SDK 为 0.13–0.22M；总 token（输入+输出）pi-ai-r3 9.46M vs SDK 3.64–4.05M（2.3–2.6 倍）。
4. **压缩不是主因。** 本分支专门给 pi-ai 加了 transcript 压缩：48k 预算下 pi-ai 折叠了 1,275–1,522 个工具输出、把单请求输入压到 ≤76K；SDK 路径不压缩（单请求最大 223K）。即使如此，pi-ai 仍然更贵；把预算抬到生产默认的 160k（r3）也没有改变结论。
5. **换一个更小的 PR 复核，结论一致**：6 文件 / 10 KB 的 PR #7191 上，pi-ai 用 8.7 分钟 / 2.19M tokens，SDK 用 2.7 分钟 / 0.71M tokens（均约 3.1 倍）。放大不是大 PR 特有的现象。
6. **生产环境核对**：103 的 PR Manager 当前未设置 `ARGUS_OPENAI_RESPONSE_IMPL`（默认 `sdk`），依赖的 code-argus 1.9.0 中还没有本分支的压缩修复。也就是说，昨天现场观察到"更贵"发生在没有压缩的 pi-ai 路径上；本次实测说明即使带上压缩修复，pi-ai 也仍然更贵。
7. **两个最可疑的实现差异已被单变量实验排除**：把 pi-ai 的首条指令从 `developer` 换成 `system`、或去掉 `max_output_tokens=32768`，轮数都没有收敛（详见 §九）。
8. **根因已定位：pi-ai 的 reasoning 重放策略。** `ARGUS_OPENAI_REASONING_REPLAY` 只在 pi-ai 实现里生效（默认 `drop`，逐轮剥离模型自己的推理），SDK 实现根本不读这个开关、始终重放带 `encrypted_content` 的 reasoning item。把 pi-ai 切到 `keep` 后，同一 PR 上立刻收敛到 SDK 量级（5.0 分钟 / 67 请求 / 1.67M tokens vs SDK 4.2 分钟 / 58 请求 / 1.42M）。**生产 103 未设置该开关＝pi-ai 走 `drop`**，这就是现场"切 pi-ai 后更贵"的原因——不是协议栈本身的差异。
9. **修复后多 PR 复验：两实现无系统性差异（见 §十一）。** 4 个真实 PR（10–68 KB）上 pi-ai/SDK 的 token 比值 0.58×–1.40×、均值 ≈1.0×；缓存率两边同为 84–93%（稳态 87–93%），未命中 input 几乎相同。

> 建议：若要继续用 pi-ai，给它显式设置 `ARGUS_OPENAI_REASONING_REPLAY=keep`（或重新审视 `drop` 这个默认值——它本意是省成本，实测反而贵 2–3 倍）；SDK 侧要么让它同样尊重该开关，要么在文案上说明它实际等价于 keep。压缩与统计修复可随分支一起发布。

## 三、时间与节奏

- 48k 的两轮 pi-ai 都没跑完，问题不是"某一条请求卡住"，而是**需要发出的请求太多**：同样的 4 个 reviewer，pi-ai 发了 152 / 142 / 191 条请求，SDK 只发 74 / 80 条。
- 单请求中位耗时 pi-ai 16.7–23.3 s、SDK 8.0–11.6 s；而 sdk-r2 所处的时段网关明显变慢（p90 响应 793 s、首批 4 条请求各约 14 分钟），即便如此 SDK 仍在 39.7 分钟完成——再次说明 pi-ai 的问题在请求数量而非单请求延迟。
- 请求吞吐：pi-ai 7.6 / 3.2 / 3.0 req/min，SDK 5.1 / 2.0 req/min。pi-ai 单位时间发得并不慢，但总量是 SDK 的 2–2.6 倍。

| 维度                  | pi-ai（`src/runtime/openai-responses.ts`）                                        | SDK（`src/runtime/openai-responses-sdk.ts`）                                                                   |

## 六、缓存与成本结构

- **缓存命中率不是差距来源**：pi-ai 92.7% / 94.5% / 94.8%，SDK 89.9% / 92.9%，pi-ai 甚至略高；未命中输入 pi-ai 0.41M / 0.31M / 0.44M，SDK 0.39M / 0.25M，量级接近。
- **差距集中在输出侧**：pi-ai 输出 0.57M / 0.72M / 1.04M（推理占 0.53M / 0.68M / 0.99M），SDK 0.22M / 0.13M（推理 0.20M / 0.11M）。即 pi-ai 侧每个 reviewer 都"想得更多、说得更多"，并且请求更多。
- 因此省钱的杠杆在"减少轮数/工具调用"（实现形态：developer role、`max_output_tokens`、工具协议、压缩策略），而不是缓存策略。
- 第二个 PR 的结论一致（pi-ai 缓存命中 90.9% vs SDK 83.2%，差距同样在总量而非命中率）。

## 九、单变量实验：根因是 reasoning 重放策略

方法：同一个 PR #7191、同一时间窗（07:00–08:50 UTC）内串行运行，其余参数完全相同；变量用运行时开关或线级改写注入，并都从 tap / 请求载荷核对确实生效。

| 运行                      | 变体                                     | 用时                  | 请求数       | 总 token              | 状态     |
| ------------------------- | ---------------------------------------- | --------------------- | ------------ | --------------------- | -------- |
| sdk-p2 / sdk-p2b / sdk-p3 | SDK 锚点 ×3                              | 2.7 / 4.1 / 4.2 min   | 37 / 43 / 58 | 0.71M / 0.86M / 1.42M | 全部跑完 |
| pi-ai-p2 / p2b            | pi-ai 基线（drop 推理）                  | 8.7 min / 20 min 上限 | 87 / 119     | 2.19M / 3.55M         | 一次中断 |
| pi-ai-p2d                 | 首条指令改 `system`                      | 12.4 min              | 100          | 2.75M                 | 跑完     |
| pi-ai-p2n                 | 不发 `max_output_tokens`                 | 20 min（上限）        | 96           | 2.76M                 | 中断     |
| pi-ai-p3a                 | 显式 `parallel_tool_calls:false`         | 17.4 min              | 117          | 3.25M                 | 跑完     |
| pi-ai-p3b                 | 系统提示词对齐 SDK 文本                  | 20 min（上限）        | 80           | 2.48M                 | 中断     |
| **pi-ai-p3c**             | **`ARGUS_OPENAI_REASONING_REPLAY=keep`** | **5.0 min**           | **67**       | **1.67M**             | **跑完** |

前四组（developer→system、无 `max_output_tokens`、`parallel_tool_calls:false`、SDK 系统提示词文本）全部阴性；唯一收敛的是 **keep**：pi-ai 立刻回到 SDK 量级（5.0 分钟 / 67 请求 / 1.67M vs 同窗 SDK 4.2 分钟 / 58 请求 / 1.42M）。分 agent 工具调用数：security 11、performance 13、logic 23、style 10（drop 基线为 35–79 / 19–60 / 29–98 / 12–35）。

机制证据（代码 + 载荷）：

- `ARGUS_OPENAI_REASONING_REPLAY` 只在 pi-ai 实现里被读取（`src/runtime/openai-responses.ts:592,698`），默认 `drop`；SDK 实现完全不读它。
- `drop` 下 pi-ai 会把会话里的 reasoning item 全部剥掉：tap 实测 pi-ai 各轮 0 条请求带 reasoning；SDK 则始终重放（58 条请求中 47 条带 reasoning，内容含模型此前的 `reasoning_text`，例如 "Let me analyze this diff from a security perspective…"，另附 `encrypted_content`）。
- 模型看不到自己此前的分析就会反复重新探索——这正是 2–3 倍轮数/成本差距的来源。切到 `keep` 后两侧请求都带 reasoning item，行为随即一致。
- 顺带核对：工具定义两侧完全相同（同为 5 个工具、相同 description/parameters/strict，仅 `report_issue` 的 `required` 顺序不同）；任务提示词约 17.2KB 两侧字节级相同。

生产含义：103 的 `.env` 未设置 `ARGUS_OPENAI_REASONING_REPLAY`，pi-ai 走默认 `drop`——这直接解释了"切到 pi-ai 后时间和 token 都增加"。修复方向二选一：① 给 pi-ai 部署显式设置 `keep`；② 重新审视 `drop` 默认值本身（设计意图是省成本，实测反而贵 2–3 倍）。SDK 实现实际等价于 keep，也建议在文档中写明。

落地情况（2026-10-15）：已按结论**移除该开关**——`refactor(runtime): remove the pi-ai reasoning-replay drop mode`（commit `61e1d81`，code-argus 分支 `codex/pi-ai-cost-stats-fixes`，更新 [PR #28](https://github.com/jimwei/code-argus/pull/28)）。pi-ai 现在固定保留原生推理重放，与 SDK 行为一致；README（中英）与 reasoning 探针文档同步更新，全量 372 项测试、类型检查、Prettier/ESLint 通过，独立复核未发现 P0/P1 问题。

## 十、大 PR 复验与残留放大原因（2026-10-15 09:07–11:27 UTC）

修复 reasoning 重放后，在大 PR #7182 上复跑同窗对照（48k 预算、新构建），发现 pi-ai 仍有约 1.5 倍 token 差（3.32/4.22/4.69M vs SDK 2.21/2.50M），于是做了一轮变量扫描（每项 1–2 次）：

| --------------------------------------- | ----------------------- | ------------- | -------------------------- |
| 基线（keep，未搬运指令）                | 6.44 / 6.71 / 13.20 min | 80 / 103 / 78 | 3.32 / 4.22 / 4.69M        |

| 系统提示词换成 SDK 文本                 | 6.98 min                | 119           | 5.18M                      |

| 去掉 `include`/`summary`                | 6.91 min                | 75            | 3.85M                      |

## 十二、#7182 深度调查：pi-ai 为什么在 token 与缓存率上"落后"

### 结论

1. **token 的"落后"主要来自一次失败的 agent 重试。** pi-ai-p5 的 logic-reviewer 第一轮里有一个请求把输出预算（`max_output_tokens=32768`）全部花在推理上：上游返回 `response.incomplete (reason=max_output_tokens)`，runtime 依约把这一轮作为 `incomplete` 交给编排层，编排层按"失败重试"整轮重跑了该 agent。**第一次尝试的 622,792 token 被丢弃**（这也解释了 68 vs 58 的多余请求、11.0 vs 4.98 分钟的墙钟）。扣掉这次浪费，该轮实际消耗 **2,322,826 token**，落在 SDK 的 2.21–2.50M 区间之内。
2. **缓存率的"落后"是同一件事的副产品。** 被丢弃的那次尝试是"新会话起步"（前几轮命中率低），把整轮平均缓存率从 **92.7% 拉低到 91.5%**；扣掉它之后 pi-ai-p5 的缓存率（92.7%）高于 sdk-p4（91.4%）与 sdk-p4b（91.9%）。
3. **pi-ai-p5b（无重试）与 sdk-p4b 的 1.22× 差是运行间波动**：差异集中在 style-reviewer（17 轮 / 469K vs 11 轮 / 223K）；SDK 自己在同一 PR 上的波动是 **2.21–4.00M（1.8×）**，比这个差距还大。
4. 因此 #7182 上不存在"pi-ai 结构性更贵或缓存更差"；剩下的是一个**可用性缺陷**：输出预算耗尽会让整轮 agent 白跑（约 1/7 的运行会撞到）。

### 证据链

- stderr：`Agent logic-reviewer 失败 (尝试 1/2): Agent logic-reviewer failed: runtime returned incomplete, 将在 2s 后重试...`（11:18:30）；该运行 `agent:start` 事件 5 次（其余三个 agent 各 1 次，其余 6 个 pi-ai 运行都是 4 次）。
- tap：id=48 的响应 `http 200 / output_tokens=32768 / reasoning=32768 / terminal=response.incomplete / reason=max_output_tokens`。
- 会话链分析（按 item 前缀归链）：5 条 reviewer 链 + 1 条 validator 链，其中 chain#1（10 轮、550,387 input、总计 622,792）不属于任何 `Agent-Summary`——正是被丢弃的第一次 logic 尝试。
- 全量统计：#7182 的 7 次运行里，pi-ai 有 1 次触发该事件、SDK 0 次（SDK 从不发送 `max_output_tokens`）。

### 机制

pi-ai 路径给每条请求都带 `max_output_tokens: 32768`（来自模型定义）。某一轮推理特别长时（本例整轮 32,768 token 全是 reasoning），上游以 `response.incomplete` 结束；runtime 将这一轮作为 `incomplete` 返回给编排层，编排层按失败重试整轮 agent。SDK 路径不发该参数，所以从不触发。runtime 里已有的 `escalateMaxOutputTokens` 目前只用于文本生成路径，未覆盖 agent 轮次。

### 方案与验证

- **A（推荐）**：在 pi-ai 的 agent 循环内做单次预算升档重试——遇到 `stopReason=length` 时把该请求升到 65536 重发一次，仍失败才按 `incomplete` 返回。单次代价 ≤65K token，避免整轮 ~600K 的白跑。
- **B**：agent 轮次不发送 `max_output_tokens`（与 SDK 请求形态一致，从根上消除该失败模式；代价是失去"防跑飞"上限）。
- C：不改代码（当前行为）——实测每次触发约浪费 600K token + 4 分钟，概率约 1/7。

## 十五、performance-reviewer 差距的深挖与修复（2026-10-16）

### 差距为什么这么大（#7182，pi-ai vs SDK）

- pi-ai 的 performance agent 用了 **26 轮 / 43 次互不重复的工具调用**（前 19 轮每轮
  两个并行调用），SDK 同 agent 21 轮——不是卡在重复调用，是探索量真的翻倍。
- pi-ai 每轮重放完整 transcript（含从 `thinkingSignature` 重建的推理项），请求体积

     token）+ 最近内容让保留项长期高于水位 ⇒ 一个都不折，只在首次超预算时告警一次。

1. 估算器改为按实际发送的 `thinkingSignature` 计体积。
2. 折叠时**整块移除较早回合的思考块**（保守保留最近 4 个 assistant 回合）。其间验证过

3. 折叠门槛放宽：低水位不可达时，只要一次能省 ≥ max(8K, 超量的 1/2) 仍执行折叠，
